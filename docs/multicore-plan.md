# 多核优化改造方案

目标：在**不破坏联机确定性**的前提下，把 gamemd.exe 的单线程逻辑帧拆到多核上。

---

## 0. 一句话前提

RA2/YR 是**确定性锁步**。这条约束压倒了所有其它考虑：

> 所有机器必须在每一逻辑帧算出**逐位相同**的状态。
> 因此并行的合法范围只有两个：
> 1. 一帧**内部**，把互不依赖的子任务分给多个核；
> 2. 一帧**内部**，把同一子任务按数据区间切分（data-parallel）。
>
> **不能**跨帧并行，**不能**引入依赖完成顺序或浮点累加顺序的归约。

依据：`Queue.CPP` 的 `0x006475F0` 同时引用
`"Processing Ticks:%03d Frames:%03d"`、`"Wait_For_Players returned %d"`、
`"Frame %d, my sent = %d"`；以及大量 `"*** CRCs"` 日志。

---

## 1. 现状：单帧里都干了什么

从主循环 `0x0055E420`（MainLoop.CPP）的调用图反推，一帧大致是：

```
采集输入  ->  收网络包(0x00541820)  ->  推进锁步帧(0x006475F0 -> 0x00648710)
         ->  对象 AI / 移动 / 战斗  ->  寻路  ->  视野  ->  渲染
```

原引擎把这些全排在一条时间线上。瓶颈通常来自三处：

| 热点 | 依据 | 特征 |
|---|---|---|
| **寻路** | `0x0042C900`，两级（分层 + 常规 A*） | 计算密集，请求之间天然独立 |
| **对象 AI / 移动** | RTTI 里 `DynamicVectorClass<TechnoClass*>` 等容器 | 数量大，但相互耦合（避让、攻击目标） |
| **视野 / 战争迷雾** | `FoggedObjectClass`、`LightSourceClass` | 计算密集，只读为主 |

---

## 2. 分级改造路线

按"收益 / 风险"排序，从最安全的一档做起。**每一档都必须能通过
`src/main.cpp` 那样的串行 vs 并行逐位比对测试。**

### 第 1 档：寻路并行（已完成，收益 3.5~3.85x）

- 入口：`PathFinder::Solve_Parallel`（`src/ai/PathFinder.cpp`）
- 做法：一批寻路请求交给 `TaskSystem`，结果按 ticket 下标写回固定槽位。
- 为什么安全：每条路径互不影响；写回位置由下标决定，与完成顺序无关。
- 实测（128×128 地图 / 256 条请求 / MSVC /O2）：

  | | 串行 | 并行 | 加速 |
  |---|---:|---:|---:|
  | 每次寻路现场分配缓冲 | 94.6 ms | 106.4 ms | **0.89x（更慢）** |
  | 线程局部缓冲 + 时间戳免清零 | 85.2 ms | 22.2 ms | **3.85x** |

  > 第一行是真实踩过的坑：**不先消除分配开销就直接并行，只会更慢**。
  > 寻路本来是 CPU 密集，但当每次调用都要 new/清零两个 16384 元素的数组时，
  > 时间全花在内存分配上，多线程把分配器争抢得更厉害。
  > 这一条对原引擎同样成立——改多核之前必须先做内存分配优化。

- 待办：还原真正的分层规划（见 §4）。当前 `Hierarchical_Find_Path`
  退化为常规 A*，行为正确但没拿到分层的收益。

### 第 2 档：视野 / 迷雾重算并行

- 只读地图与单位位置，写每个格子的可见性位。
- 切分方式：按**行区间**切分地图。
- 风险点：相邻行之间是否有写重叠。需要先确认原引擎的 LOS 算法
  是否在扫描过程中读到自己刚写的值——如果是，就必须双缓冲。

### 第 3 档：对象更新并行（最复杂）

- RTTI 里 Techno 由 `DynamicVectorClass<TechnoClass*>` 集中管理，
  天然是连续数组，可以区间切分。
- 但对象之间**有耦合**：避让要看邻居占位，攻击要读写目标血量。
- 推荐做法：**收集-应用两阶段**
  1. 阶段 A（可并行）：所有对象只**读**上一帧的世界快照，
     计算出"意图"（移动向量、伤害值），写进各自的意图槽，不碰世界状态；
  2. 障碍：按固定顺序（对象 ID 升序）串行裁决意图冲突；
  3. 阶段 B（可并行）：把裁决后的结果写回世界。
- 关键在于阶段 A **只读**、阶段 B **只写各自对象**，
  裁决阶段保持固定顺序 —— 这样结果与串行逐位一致。

### 第 4 档：渲染与逻辑分离

- 渲染是 DirectDraw（`DDRAW.dll` 仅导入 `DirectDrawCreate`）。
- 逻辑 15 FPS、渲染跑满刷新率，两者用**双缓冲状态**解耦：
  逻辑帧写完快照后，渲染线程只读快照。
- 这一档不改逻辑语义，风险最低，但需要先把渲染读到的状态全部快照化。

## 3. 明确不要做的事

| 反模式 | 后果 |
|---|---|
| 跨帧投机执行（提前算下一帧） | 下一帧输入可能未到，回滚代价高且易失步 |
| 并行归约用浮点累加 | 加法不满足结合律，不同线程划分结果不同 |
| "谁先算完用谁的" | 直接破坏确定性 |
| 在并行区内调用原引擎的全局单例 | 原代码大量使用全局变量，必须先隔离 |
| 用 `shared_mutex` 粗粒度锁住整个地图 | 争用会让并行退化成串行甚至更慢 |

## 4. 还需要补的逆向工作

按优先级：

1. **虚表 → 类名映射**。虚表已定位 1026 张（其中 800 张有代码引用），
   并用 `tools/vtmap.py` 推断出了主继承链（见 `docs/binary-baseline.md` §11）：
   109 槽的共同基类下有 9 张 122 槽的派生族，再往上 123/124/125/128 槽逐级派生。

   **已经试过并且失败的路**：靠"引用虚表的函数所引用的字符串"反推类名。
   实测 231 张里只有 6 张有弱线索（"Battles"、"ScriptTypes" 之类），
   根本不够——构造函数不引用类名字符串，这条路走不通。

   **接下来该做的**：看每张虚表对应的构造函数具体初始化了哪些字段，
   再与 INI 段名交叉验证。`tools/vtmap.py` 已把引用函数逐条列出，
   `db/vtmap.json` 里可以直接查。

2. **`sizeof(CellClass)` 与字段偏移**。抓手：`0x005659F0`
   （`MapClass::Init_Clear`）里的缓冲区分配；`0x00652E90`
   （`RadarClass::Init_For_House`）的循环步进。

3. **分层寻路的区域图**。RTTI 提供了类：`MapRegionClass`、
   `PlanningNodeClass`、`PlanningBranchClass`、`PlanningMemberClass`、
   `PlanningTokenClass`。入口在 `0x0042C900` 里
   "Hierarchical findpath failure" 分支的上方。

4. **对象容器布局**。`DynamicVectorClass<T>` / `VectorClass<T>` 的
   模板实例在 RTTI 里有 660 个，说明这是引擎的主力容器；
   它的内存布局决定了能否安全地按区间切分对象数组。

## 5. 回归验证

- **确定性**：`src/main.cpp` 的串行 vs 并行逐位比对，任何并行改动都必须通过。
- **失步检测**：保留并强化原引擎的 CRC 机制（二进制里有
  `"*************** Building CRCs"` 等大量 CRC 日志），
  每帧输出一次校验和，两台机器不一致立即报错。
- **性能**：`LoopStats` 记录每个阶段的耗时均值，
  改造前后可直接对比（`src/engine/GameLoop.h`）。
