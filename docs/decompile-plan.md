# 整体反编译计划（`gamemd.exe` `.text` → 可读 C++）

> `docs/restoration-plan.md` 定的是**产品**路线（P0 素材 → P5 多核）。
> 本文定的是**方法**路线：把 4,060,045 字节的 `.text` 变成"有名字、有签名、
> 有调用关系、有伪代码"的代码这一半，怎么一步一步做完、每一步怎样算做完。
>
> 两件事的关系：P3 之后剩下的工作（其余类的字段名、游戏逻辑、锁步、多核改造）
> 全都卡在同一件事上 —— **函数这一层还没有**。所以先补这一层。

---

## 0. 目标与验收

**目标**：`.text` 里每一个代码字节都能回答四个问题 ——
属于哪个函数、叫什么、收什么参数、别人怎么调它 —— 并最终能输出可读的 C++。

**"做完了"分四级，逐级可验收**：

| 级 | 判据 | 现在的状态 |
|---|---|---|
| **L1 骨架** | `.text` 每一字节被归类（代码 / 填充 / 数据 / 未知）；每个代码字节**唯一归属**一个函数；`0x401000–0x7C0000` 段函数入口 **100%** 落在 16 字节边界 | ✗ 函数清单里有 22,087 条线性兜底产物混在真函数里（对齐率 4.1%，见 §2.1） |
| **L2 关系** | 每个函数有入边 / 出边 / CFG / 签名（调用约定 + 参数字节）；虚调用点标出可能的类 | ✗ 只有出边，无入边、无基本块、无签名 |
| **L3 语义** | 每个函数能输出结构化伪代码（`if/while/for/switch` + 表达式树）；虚方法带 `类::槽位` | ✗ 没有 |
| **L4 源码** | 按 `__FILE__` 分组成 58 个翻译单元，能编译 | ✗ 没有 |

**明确不做**（否则范围失控）：

- 不追求逐字节等价于原版源码。2001 年的 MSVC 已经不可复现，
  "编译回去得到同样的机器码"不是可达到的判据，本文改用**指令序列相似度**（§6.2）。
- 不还原 CRT / 静态库内部实现（`0x7C0000` 往上那 128 KB）。识别出"这是 `operator new`"
  就够了，里面逐行怎么写与多核目标无关。
- 不还原 `Blitter` 家族（`restoration-plan.md` §0.2 已作废）。

## 2. 缺口：为什么现在还不能直接开始写 C

### 2.1 函数清单不成立（最要命）

`db/functions.json` 现有 28,827 条，按来源分：

| 来源 | 条数 | 入口 16 字节对齐率 | 判定 |
|---|---:|---:|---|
| `entry` | 1 | — | 真 |
| `call` | 6,635 | **93.4%** | 真（非对齐的 478 条**全部**落在 `0x7C0000` 以上，见 §3） |
| `prologue` | 104 | 59.6% | 一半是噪声 |
| `gap` | **22,087** | **4.1%** | **不是函数**，是"线性兜底" |

`gap` 条目尺寸合计 **4,203,245 字节 —— 比整个 `.text` 还大**，说明它们大量互相重叠、
也大量压在真函数上。所以文档里那句"覆盖 .text 99.2%"是**循环论证**：
它由一堆不知道自己边界的区间拼出来，不能当作"我们认识这 99.2%"。
这张表现在能用的只有那 6,740 条。

### 2.2 虚表槽这条通道完全没接

`db/rtti.json` 有 **14,035 个虚表槽 / 6,686 个去重目标**。这些是 C++ 虚方法，
只被间接调用（`call [eax+0x94]`），所以**永远不会**被 `call rel32` 播种找到。

实测缺口：

| | 数量 |
|---|---:|
| 虚表槽去重目标 | 6,686 |
| 其中已被 `entry`/`call`/`prologue` 找到 | **455（6.8%）** |
| 只被 `gap` 兜到（边界大概率是错的） | 528 |
| **两条通道都没找到** | **5,703** |

随机抽 14 个"没找到"的目标反汇编，**14/14 都是标准函数入口**
（`push esi / mov esi,ecx`、`sub esp,0xf0 / push esi / mov esi,ecx`、`push 0x344 / call …`）。

**这两个通道的并集 = 12,971 —— 函数数的下界。**（旧值 6,740 连一半都不到。）

### 2.3 跳表没有跟

`jmp dword ptr [reg*4+disp]` 有 **387 处**，其中 **349 处**能在该地址读出连续 ≥3 个
指向 `.text` 的表项，表项合计 **2,778 个**、去重目标 **2,646 个**。

`FunctionFinder._walk()` 只跟 `X86_OP_IMM` 操作数，**完全忽略跳表**。
后果：带 `switch` 的函数体被截断，`case` 分支要么丢掉（变成 `gap`）、
要么被合并进别的函数（边界错）。

### 2.4 没有 CFG、没有调用图、没有签名

现有条目只有 `calls`（出边）和 `strings`。没有入边、没有基本块、没有参数。

**而签名有一条现成通道被浪费掉了**：31,058 条 `ret` 指令里，带立即数的有 22 种：

| `ret N` | 条数 | 含义 |
|---|---:|---|
| `ret 4` | 7,641 | `__stdcall`，1 个 dword 参数 |
| `ret 8` | 3,941 | 2 个参数 |
| `ret 16` | 2,086 | 4 个参数 |
| `ret 12` | 1,651 | 3 个参数 |
| 其余 18 种 | 1,142 | 5–12 个参数 |

这直接给出 `__stdcall` 的参数字节数，**不需要任何推断**。

### 2.5 没有代码生成

这一层是从零开始（§4 讨论要不要借力）。

## 3. 一个关键发现：函数入口的 16 字节对齐律

这是本轮测量最有价值的产物，三条用途都在下面。

把"强证据入口 ∪ 虚表槽目标"按地址分段统计 16 字节对齐率：

| 地址范围 | 入口数 | 16 字节对齐 | 对齐率 |
|---|---:|---:|---:|
| `0x401000 – 0x7C0000` | 12,374 | **12,374** | **100.0%** |
| `0x7C0000 – 0x7E038D` | 597 | 118 | 19.8% |
| 合计 | 12,971 | 12,492 | 96.3% |

独立佐证：`db/sources.json` 里由 `__FILE__` 断言字符串定位的 **213 个函数，
VA 低 4 位全部是 `0x0`**（213/213）。这条证据来自完全不同的通道（字符串引用），
和上面的 `call`/虚表两条通道算出来的结论一致。

**结论**：`0x7C0000` 以下那段是游戏本体代码，编译时函数按 16 字节对齐；
`0x7C0000` 以上那 ~128 KB 是运行时库（静态链接的 CRT / 启动代码），
编译选项不同，不遵守这个对齐。

**三条用途**：

1. **Stage 1 有一条可失败的硬判据**：重建结果里，`0x401000–0x7C0000` 段内
   任何函数入口不落在 16 字节边界 → 直接判错。这不是"差不多就行"，
   是 12,374/12,374 的实测。
2. **边界推广**：`gap` 里对齐 16 字节的起点才**可能**是入口（4.1% 的现状说明
   另外 95.9% 根本不是入口）。
3. **`0x7C0000` 这条分界线本身是个待解释的事实**，不是噪声。
   Stage 1 要把它查清楚（是链接顺序？是 `/O1` 编译的库里码？），
   而不是把 478 个例外当误差抹掉。

## 4. 分阶段路线

每阶段都写清：**输入 / 方法 / 证据 / 产物 / 对账（怎样算通过、怎样算失败）**。
标 ★ 的是"只有我们这种已有语义资产的项目能做"的步骤。

### Stage 1 — 函数边界重建　← 本轮执行

- **目的**：产出一份**每个入口都有证据**的函数清单，替代现在那张真假混装的表。
- **输入**：`gamemd.exe`、`db/rtti.json`（虚表）、`db/sources.json`（对账用）。
- **方法**：
  1. **分档播种**（按证据强度）
     - `entry` — PE 入口点。
     - `vtable` — 虚表槽目标（新增通道，§2.2）。
     - `call` / `tailjmp` — 从**已到达**代码里跟出来的直接调用/尾跳目标，
       用**迭代到不动点**的方式扩散（旧实现是一次性扫全 `.text` 的立即数，
       数据里碰巧解出来的 `call` 也会进播种集）。
     - `prologue` — `55 8B EC` 且**入口对齐 16 字节**（新增约束，把 59.6% 提到接近 100%）。
     - `dataptr` — `.rdata`/`.data` 里指向 `.text` 的 4 字节值，排除虚表槽与跳表本身（弱档）。
  2. **过程内递归下降**，比旧实现多两件事：
     - **跟跳表**：遇到 `jmp [reg*4+disp]` 读表，把落在窗口内的表项全部入栈（§2.3）。
     - **尾调用判定**：`jmp` 目标落在 `[entry-0x2000, entry+0x8000]` 之外 → 记为尾调用出边，**不并入本函数体**。
  3. **缺口分类**（替代旧的"gap 一律当函数"）：把 `.text` 每个字节标成
     - `code`（属于某个函数）
     - `pad`（连续 `0x90` / `0xCC` 填充：实测 `0x90` 连续 ≥4 字节有 14,922 段 / 146,873 字节）
     - `data`（跳表本体等，由跳表解析反推）
     - `unknown`（既不是以上，也不在任何函数里）—— **逐个列出来，不掩盖**
  4. **逐函数属性**：`ret` 种类与 `ret N`（→ `__stdcall` 参数字节）、
     `sub esp,N` 栈帧、是否写 `fs:[0]`（SEH）、是否 leaf、是否是
     `jmp [IAT]` 形式的导入 thunk、`call __chkstk` 标记大栈帧。
- **证据**：入口对齐律（§3）、`ret` 形态、填充统计。
- **产物**：`db/funcs.json`、`docs/functions.md`、`src/re/FuncTable.h`（给 C++ 侧的查询表）。
- **对账（可失败）**：
  1. `0x401000–0x7C0000` 内入口 16 字节对齐率必须是 **100%**（现状 96.3%）。
  2. `db/sources.json` 的 213 个函数 VA 必须**全部**在结果里。
  3. 函数区间两两不重叠。
  4. 每个函数必须终止于 `ret` 或越界 `jmp`。
  5. 旧表的 `call` 档 6,635 条必须全部保留（新结果只能多不能少）。
  6. `unknown` 字节数必须降到 `.text` 的 1% 以下，且**逐段列出并解释**。
  7. `.text` 每个字节恰好属于 `code`/`pad`/`data`/`unknown` 之一。

### Stage 2 — 基本块与 CFG

- **方法**：以函数为单位切基本块（入口、分支目标、分支下一条）；边分四类：
  `fallthrough` / `jcc` / `jmp` / `switch`（跳表展开成 N 条带 case 值的边）。
- **产物**：`db/blocks.json`。
- **对账**：每个函数的块图强连通分量与 `ret` 数量一致；跳表边数 == 表项数。

### Stage 3 — 调用图与签名

- **方法**：
  - 入边/出边建立，标出递归环与互相递归组。
  - **虚调用点**：`call [reg+slot*4]` → 用 `db/rtti.json` 的槽语义反推可能的类集合与
    方法名（同一槽位在不同类里的语义是已知的）。
  - **签名**：`ret N` → `__stdcall` 参数字节（§2.4）；`add esp,N` 在调用后 → `__cdecl`
    参数字节；`mov this,ecx` 在函数头 → `__thiscall`；寄存器传参 → `__fastcall`。
  - 参数个数与"调用点压栈次数"互相印证（两个独立来源）。
- **产物**：`db/callgraph.json`、`docs/signatures.md`。
- **对账**：`ret N` 推出的参数字节必须等于所有调用点压栈字节数的**众数**；
  不符的逐个列出。虚调用点的目标集合必须包含实际可能的实现者。

### Stage 4 — 过程内类型传播 ★

- **方法**：把已有资产套到指令上。
  - `[reg+off]` + reg 是 `this` → 查 `FieldNameOf(cls, off)` → `this->Armor`。
  - `[reg+slot*4]` → 查虚表 → `类::方法名`。
  - 立即数指向 `.rdata`/`.data` → 查字符串表 / 全局变量表 → 命名。
  - `call` 目标 → 查 `db/names.json` / 导入表 → `MapClass::Init_Clear` / `kernel32!Sleep`。
- **证据**：字段表 6,965 条 + 字段名 381 条 + 虚表 14,035 槽 + 字符串表。
- **产物**：`db/annotated.json`（每个函数带一张"偏移 → 名字"的译注表）。
- **对账**：译注过的偏移必须 100% 能在字段表里查到；查不到的**不许编名字**，
  标成 `field_0xNNN`。

### Stage 5 — 表达式与栈变量恢复

- **方法**：栈槽 → 局部变量（合并 `[ebp-4]` 的读写链）；寄存器传播；
  `mov` 链折叠；标志位消费点回溯（`setcc`/`jcc` 还原成比较表达式）。
- **产物**：`db/expr.json`（每函数的表达式树）。
- **对账**：表达式树的叶子数 + 内部节点数与函数的指令数比值落在合理区间；
  无"凭空产生"的操作数（每个叶子必须能指到一条真实指令）。

### Stage 6 — 结构化还原

- **方法**：自然循环识别（回边 + 支配关系）→ `while`/`do-while`/`for`；
  分支合并 → `if`/`else`；跳表 → `switch`；短路求值 → `&&`/`||`；`?:` 还原。
- **产物**：C 伪代码文本。
- **对账**：伪代码重新走一遍编译器的 CFG 构造，与原 CFG **同构**（同块数、同边数）。
  这是**不依赖"编译回去字节相同"的等价判据**。

### Stage 7 — 翻译单元重组

- **方法**：用 `db/sources.json` 的 58 个 `__FILE__` 把函数归到文件；
  对没有 `__FILE__` 线索的（213/12,971 ≈ 1.6%），按"谁调用谁 + 共享全局变量"
  做社区发现，给出候选分组并**标注置信度**。
- **产物**：58+ 个 `.cpp` 骨架（函数体先留空，只有签名与调用关系）。
- **对账**：有 `__FILE__` 的函数分组必须唯一且互斥；候选分组的函数
  必须与已有分组的函数在调用图上相邻。

### Stage 8 — 验证

见 §6。

## 5. 复用还是自制

**本机现状**：`ghidra` / `ida` / `retdec` / `radare2` / `objdump` 都没有；
有 **JDK 25**（`C:\Program Files\Eclipse Adoptium\jdk-25.0.4.101-hotspot`）。

三条路：

| 路线 | 优点 | 缺点 | 适用阶段 |
|---|---|---|---|
| **A 全自制** | 与已有资产天然打通；每步都能对账；没有外部依赖 | S5/S6 是从零写编译器前端，工作量最大 | S1–S4、S7–S8 |
| **B 引入 Ghidra headless** | S5/S6 直接白送，能处理 3 万函数 | 需下载 ~400 MB + 脚本对接；它的输出**不知道 RA2 的类名**，仍要回灌 S4；产生的中间数据格式不归我们控制 | S5/S6 |
| **C 混合** | 骨架用自制的（可对账），重活用现成的 | 需要设计"回灌接口" | 全部 |

**建议 C**，理由是分工线很清楚：

- S1–S4 是**唯一**能把字段表/虚表/INI 键表用起来的部分，通用反编译器做不到，
  而且我们已经完成一半（`fieldscan.py` / `fieldname.py` / `layout.py` 都在跑）。
- S5–S6 是纯机械重活 —— 支配树、循环识别、表达式折叠、类型推断 ——
  自己写要几个月，且**没有 RA2 特殊性**，借力不丢信息。
- **接入判据**（避免"先接一半永远接不完"）：S1–S4 全部通过各自对账后，
  再评估 S5–S6。若 S5 自制的第一版在两个星期的等价工作量内做不到
  "块级 CFG 同构"，就转 B。

## 6. 验证策略（三级，从便宜到贵）

### 6.1 结构性对账（每轮都跑，秒级）

- 入口 16 字节对齐律（§3）。
- 与 `db/sources.json` 的 213 个函数、`db/rtti.json` 的 14,035 个槽位交叉：**一条不许少**。
- 区间不重叠、不越界、终止于 `ret`/越界 `jmp`。
- `.text` 字节分类不漏不重。
- 与 C++ 侧 `src/re/FuncTable.h` 的硬断言一致（沿用 `FieldNames_Check()` 的做法）。

### 6.2 语义性对账（本地可做，分钟级）

**抽样重编译比对**：取 N 个函数，把反编译出的伪代码补成能编译的 C，
用本机 MSVC（`tools/build.py` 已经有找到 `cl.exe` 的能力）按同样优化选项编译，
比较**指令序列相似度**（用最长公共子序列比例，不用字节相等）。

- 阈值：相似度 ≥ 0.9 记为通过。
- 这是**可以失败的**判据，且不依赖"编译器可复现"这个达不到的前提。
- 先在**已经有人工确认语义**的函数上做（`Read_INI` 那批、寻路那批），
  这样"相似度低"能立刻区分是"反编译错了"还是"原版就该不一样"。

### 6.3 差分执行（最贵，只在关键路径做）

对纯函数（无全局副作用、无 I/O）做函数级差分：同一组输入，
原版二进制 vs 还原实现，比较输出与全局内存的差异。
`src/ai/PathFinder.cpp` 那条"并行与串行逐位一致"的回归就是这个思路，
可以推广到更多纯函数。

## 7. 风险与已知的硬骨头

| 风险 | 说明 | 对策 |
|---|---|---|
| **手写汇编段** | 2001 年的游戏里有 MMX/SSE 手写循环（体素光栅化、混色） | 不还原成 C，**原样保留为 `.asm`** 并在伪代码里标 `__asm_block` |
| **C++ 异常 / SEH** | x86 用 `fs:[0]` 链表，没有 `.pdata` 表可查 | Stage 1 先只**标记**（写了 `fs:[0]` 就记 `has_seh`），不做结构化还原 |
| **COMDAT 折叠** | 相同函数体被合并，虚表槽指向同一地址（实测 `0x4C9150` 被 **205 个槽**引用） | 这是**特性不是 bug**：一个函数体服务多个类，归属要记成集合 |
| **内联 / 模板实例化** | 一个 `__FILE__` 对应多个地址区间 | Stage 7 的分组必须允许一对多 |
| **`__FILE__` 只覆盖 1.6%** | 58 个文件、213 个函数。剩下 98% 没有源码结构线索 | Stage 7 的候选分组必须带置信度，不假装确定 |
| **`.text` 里的数据** | 跳表可能就在 `.text` 内 | Stage 1 的解析结果反过来标注 `data` 区间 |
