# 函数边界重建（全量反编译 Stage 1）

> 产物由 `tools/funcscan.py` 生成，可重跑。
> 方法、阶段划分与验收判据见 `docs/decompile-plan.md`。

## 1. 为什么重做这件事

旧清单 `db/functions.json` 有 28,827 条，但其中 **22,087 条是「线性兜底」的产物** —— 它们不是函数，只是"扫描到这里，前面没有函数认领，就切一段"。
证据是入口的 16 字节对齐率：

| 来源 | 条数 | 入口 16 字节对齐率 |
|---|---:|---:|
| `entry` | 1 | — |
| `call` | 6,635 | 93.4% |
| `prologue` | 104 | 59.6% |
| `gap` | 22,087 | **4.1%** |

对齐率不是「挑出来的好看数字」，它来自一个独立测得的事实：
`0x401000–0x7C0000` 段内，**直接 call 目标与 RTTI 虚表槽目标 100% 落在 16 字节边界（12,374/12,374）**；
另有一条完全独立的佐证 —— `db/sources.json` 里由 `__FILE__` 断言字符串定位的213 个函数，VA 低 4 位全是 `0x0`（213/213）。

所以 `gap` 档 4.1% 的对齐率说明：它们 96% 落在指令中间，本就不该是函数。

## 2. 这一轮补的三条通道

### 2.1 虚表槽（最大的缺口）

`db/rtti.json` 里 949 个类、**14035 个虚表槽 / 6686 个去重目标**。
C++ 虚方法只被 `call [reg+slot]` 间接调用，**永远不会**被 `call rel32` 播种找到。
实测：其中只有 **455 个（6.8%）** 曾被旧清单的强证据通道找到。

### 2.2 跳表

`jmp dword ptr [reg*4 + 表址]` 实测 387 处（绝对形式），解析出 **331 张跳表 / 2706 个表项**；
另有 0 处「表址在寄存器里」的形式（`lea reg,[tab]; jmp [reg+reg*4]`），本轮不解析，只计数。
旧实现只跟 `X86_OP_IMM` 操作数，**完全忽略跳表** → 带 `switch` 的函数被子截断。

### 2.3 尾调用

`jmp` 落到跟随窗口之外 → 判为尾调用，既是本函数的出口，也是**目标函数的入口证据**。旧实现丢弃了这个信息。

### 2.4 索引锚点重同步

线性扫描只在**解码失败**时重新对齐。`.text` 里嵌着数据，数据往往能被解成一串合法指令，此时扫描会一直跑偏、再也不回来。
`tools/disasm.py` 现在支持 `anchors`：扫描一旦跨过已知入口就丢弃这条指令、改从锚点重新开始。锚点由第一遍扫描的结果算出，所以是两遍扫描。

### 5.1 本轮查清并修掉的六个成因

每一个都是先实测复现、再改代码的：

1. **锚点偏移算错**（`tools/disasm.py`）。锚点传进来的是 VA，内部要的是相对 `.text`
   的偏移，代码写成了 `VA - lo`（漏了 ImageBase），所有锚点整体偏了 `0x400000`，
   重同步机制**静默失效**。修掉之后，一批强证据入口从「不是指令起点」变为可遍历。
2. **包围盒吞函数**。函数的字节区间取的是 `[min(seen), max(seen)+len]`，是个包围盒；
   而遍历完全可能整段跳过中间（条件跳转直接跳到后面）。
   实测 `0x407040` 因此吞掉 `0x407070` 起一整簇小函数，跨度 14.7 KB。
   修法：强证据入口落在包围盒内就把末端截到它 —— 本轮截断 **7** 个函数。
3. **跳表不跟**。387 处 `jmp dword ptr [reg*4+表址]`，解析出 331 张表 / 2706 个表项。
   旧实现只跟立即数操作数，带 `switch` 的函数会被截断。
4. **出口判据太窄**。原判据只认 `ret`/`ret_imm`/`thunk`/`tails`，
   把 `loop`（`jmp $` 陷阱）、`switch`（唯一出口是跳转表）、
   `fallthru`（一路落进下一个函数的不返回跳板）三类**真出口全毙了**。
   代价是旧清单 `call` 档丢了 4 条真入口（对账第 7 条）。修法见 §6.4：
   这三类出口必须配强入口证据才收。
5. **播种通道缺一条「没人指过的函数」**。这是把 unknown 从 2.81% 压到 0.17% 的那一击。
   逐段查下来，残下来的**根本不是数据**，而是没有直接 `call` 指向的真函数：
   `0x402020`（`8b 41 14 c3`，getter）、`0x40EBC0`（`mov ecx,imm; jmp`，尾跳跳板）、
   `0x412540`（`e9 rel32`，纯 jmp 跳板）。它们只被虚表间接调用，
   而虚表通道只能覆盖 `db/rtti.json` 里那 6,686 个槽。
   判据换成**「空隙里 16 对齐处，一段能解成合法指令、且有出口的代码」**，
   并给它三条约束（候选只在未覆盖字节里取 / 入口 16 字节对齐 / 遍历硬边界就是那段空隙）：

   | 项 | 值 |
   |---|---:|
   | 轮数 | 16（收敛） |
   | 候选 | 7896 |
   | 接受（主档 = `gap`） | 591 |
   | 拒绝 | 7305 |

   拒绝原因的分布：

   | 原因 | 个数 |
   |---|---:|
   | 只剩 bound 出口且无独立证据 | 4549 |
   | 没有出口 | 2539 |
   | 不是指令起点 | 217 |

   其中 `不是指令起点` 占大多数 —— 那些 16 对齐地址落在数据串中间，
   反汇编器在那里根本没有指令边界。这正好说明该通道**没有**把数据当函数。

6. **跳表本体被当成指令解码**。锚点是**点**，跳表是**区间** —— 扫描一头扎进一张 dword 表里，那些 dword 恰好能解成一串合法指令，于是再也回不到正轨，直到撞上下一个锚点。代价有两层：

   - 表尾那个真入口**拿不到指令边界**。`0x7C7788` 是函数 `0x7C7371`内嵌跳表之后的续段，夹在表尾（`0x7C7758` 起 12 项）与下一处之间，反汇编器在那儿根本没有指令起点。
   - 函数在表前**被截断**：`0x7C7371` 一度只报到 998 字节，实际 **2,942 字节**；空隙通道只好在表里/表后造出假函数 —— 一个 `case` 标签 `0x7C77D0`（跳表 `0x7C7B3C` 的第 3 项）曾被当成「函数入口」。

   修法：把跳表本体当**数据区**交给反汇编器（`disasm.build_index(..., data_ranges=…)`），扫描进区间直接跳到区间末重开解码—— 这一步**制造**了表尾的指令边界。全局代价/收益：遮罩 331 张表 / 10824 字节，解出的指令数从 1392509 降到 1388640（**少解 3869 条**从表字节里来的垃圾指令）。

   两次都栽在同一个坑上，一并记下：

   - **`JtResolver.bytes_of` 是「起始 + 长度」，不是「起始 + 结束」。**消费方按 `range(a, b)` 用它时，`range(0x3C7758, 48)` 是**空区间** —— 逻辑静默失效，没有任何异常。`scan_dataptrs` 的「排除跳表本体」因此**从来没生效过**。现在统一走 `JtResolver.ranges()`，口径写在函数名上。
   - **生成器里的循环顶检查等于没写。** 数据区跳过最初只写在外层 `while` 顶部，而 `md.disasm` 是生成器：`pos` 落进区间后，**同一次生成器调用**会接着往下解码，顶层那次检查根本轮不到。改成每条指令之后都查一次、命中即 `break` 回外层。

另外两笔是「把不属于函数的东西正确地归位」，不是缩小分母：

- **指针表判为数据**。`.text` 里嵌着跳转表，之前全被记成 unknown。
  判据：连续 ≥3 个 dword 值都落在 `.text` 内。本轮共认出 **345 段 / 10644 字节**；
  其中此前落在 unknown 里、这轮才落上标签的是 82 段 / 314 字节（其余的早被函数体盖住或已落过标签）。
  注意**不能**假设 4 字节对齐：MSVC 常在表前垫一条 2 字节的 `mov edi,edi`，
  整张表因此是 `2 mod 4` 对齐的（实测 `0x4059D0`）。四个相位都要试。
- **孤立单字节填充**。1043 个字节形态一律是「上个函数末尾 + 1 个 `0x90` + 下一个 16 对齐的函数」，判为填充单列一类报出。

六轮的效果：

| 轮次 | 未知字节 | 当轮做的事 |
|---|---:|---|
| 1 | 522,751（12.88%） | 只有 entry / call / 虚表三条通道 |
| 2 | 142,366（3.51%） | 加「填充尽头」通道 + 遍历路标 |
| 3 | 114,216（2.81%） | 修锚点偏移 + 截包围盒 + 跟跳表 |
| 4 | 114,170（2.81%） | 补出口判据（收下 `loop`/`switch`/`fallthru` + 强入口证据）
| 5 | 7,277（0.18%） | **空隙通道** + 指针表判数据 + 孤立填充字节
| 6 | **6875（0.17%）** | **跳表本体作数据区遮罩**（表尾拿回指令边界） |

### 5.2 还没修的成因（留给下一阶段）

- **跳表里那些字节型 case 表**（`00 01 01 01 ...`）。MSVC 的密集 switch 会在
  dword 跳表后面再放一张字节索引表，长度只能从代码里推，光看字节看不出来。
  dword 部分已经被判成数据，字节部分还留在 unknown 里。
- **表址在寄存器里的跳表**（`lea reg,[tab]; jmp [reg+reg*4]`）。本轮统计为 0 处 ——
  这个数字本身要留着：它说明这条形式**没出现**，而不是我们解析过了。
- **大函数体内嵌查表数据**。这类段 S2 会给出块级证据（块之间的洞就是数据），
  这一阶段先不硬塞。

### 6.4 出口不自证、需要外部证据的函数

下表这 52 个函数**没有 `ret`**，它们靠的是另外三种出口形态：
`loop`（`jmp $`，不返回的陷阱）、`switch`（唯一出口是跳转表）、
`fallthru`（一路落进下一个函数，说明它调用的是个不返回的例程）。

这三类出口**本身不自证「这是个函数」** —— 一个 `eb fe` 也可能只是
对齐填充。之所以敢收，是因为它们同时有**强入口证据**（有 `call` 点、
或占着虚表槽）。判据写死在 `walk()` 里：弱出口必须配 `strict`。

## 8. 已知局限

- **三分之一入口只靠启发式撑着**。20138 个函数里，主档为 `padend` 的有 6185 个 ——
  它们靠的是「16 字节对齐 + 前面是填充」这条规律，而不是直接调用或虚表。
  这条规律本身是实测的（本体区 12,374/12,374），但落实到单个函数上，
  它的强度明显弱于 `vtable` / `call`。JSON 里每个条目都带 `tier`，用的时候要看得见。
- **0 个函数的边界可疑**（密度校验不过，但因为入口证据强而保留，记 `low_density`）。
- **7 个函数的末端被截断**（包围盒里撞上别的入口）。截断是对的，但它说明这些函数的内部结构还没被读懂。
- **`0x7C0000` 以上不受对齐律约束**，那段的边界质量明显低于本体区，本工具只做「有证据就采」，不假装和本体区一样可靠。
- **不做外推**：`unknown` 段不猜、不填。宁可留着，也不制造假边界。
- 重叠、无出口这类异常一律列出来，不静默丢弃。
